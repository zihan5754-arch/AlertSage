# v0.1 诊断书

这份文档是对旧版本（4 个文件、163 行）的逐条复盘，也是这次重写的依据。
写下来有三个目的：自己复盘、面试时能讲清"为什么改"、以后加功能时别把坑再踩一遍。

---

## 一、先说 star 为 0 这件事

**它不是质量指标，但也确实说明有问题。** 分开看：

### 不是质量问题的部分

- 发布 3 周、没有任何推广，公开仓库的默认曝光接近 0。绝大多数个人项目 star 都停在个位数。
- GitHub 上没有"用了就 star"的机制，star 来自：被搜索到、被推荐、被引用、有截图/演示、解决别人的具体问题。
- 一个 163 行的 demo，即便完美，也很难让人产生"我要收藏"的动机。

**结论：不要用 star 判断自己代码的好坏。** 招聘方也不会看 star，他们看：能不能跑、有没有测试、代码结构、你能否讲清取舍。

### 确实是问题的部分

这些问题不会因为"没人看"就不存在：

| # | 问题 | 后果 |
| --- | --- | --- |
| 1 | README 写"规划中：接入 LLM"，但代码里没有 | 面试官会认为你在写愿景而不是做东西 |
| 2 | 没有一张截图、一段真实输出 | 别人无法在 30 秒内判断这东西有没有用 |
| 3 | 没有测试、没有数据、没有指标 | "准不准"完全无法验证，等于自说自话 |
| 4 | 5 条正则写死在 Python 里 | 一眼看出是教程级别实现 |
| 5 | 字段是自定义的，接不了真实设备 | 无法证明你理解现场数据长什么样 |
| 6 | 命中即 `true_positive`、置信度固定 0.8 | 说明没有"误报"这个概念，而误报正是蓝队最痛的点 |

后三条是致命的：**它没有解决任何一个真实工作流中的具体问题**，只是一个"输入 payload 输出类型"的分类器。

## 二、逐文件复盘

### `app/models/schemas.py`

```python
class AlertInput(BaseModel):
    alert_type: str = Field(..., description="告警类型，如 SQL Injection")
    source_ip: str = Field(..., description="来源 IP")
    target_url: Optional[str] = ...
```

**问题**

- `alert_type` 必填且是上游已经分类好的结果 —— 那这个系统到底在判断什么？如果 WAF 已经告诉你是 SQL 注入，你再说一遍"这是 SQL 注入"没有价值。
- 没有 `asset`（资产）、`action`（是否拦截）、`status_code`、`user_agent`、`raw_log`。这几个字段恰恰是判断误报的关键：
  - 被 WAF 拦截的攻击 vs 打穿的攻击，处置优先级完全不同；
  - 扫描器 UA + 404，大概率是噪音；
  - 核心支付资产和测试环境，同样的攻击不是一个量级。
- `timestamp` 是 `str`，没有时区、没有解析。时间错了，关联和基线全废。

**改法**：见 `alertsage/models.py` 与 `alertsage/normalize.py`——字段贴合 WAF/EDR/IDS 的公共交集，时间必须解析成带时区的 `datetime`，解析失败直接报错而不是悄悄用 `now()`。

### `app/detectors/regex_detector.py`

```python
ATTACK_PATTERNS = [{"name": "SQL Injection", "pattern": re.compile(...), ...}, ...]

def detect_by_regex(alert):
    text = " ".join(filter(None, [alert.payload, alert.raw_log, alert.target_url]))
    for rule in ATTACK_PATTERNS:
        if rule["pattern"].search(text):
            return AlertVerdict(verdict="true_positive", severity=..., confidence=0.8, ...)
    return None
```

**问题**

1. **命中即定论**，`verdict` 永远是 `true_positive`。而护网里 90% 的告警是噪音——这个设计恰好把最需要解决的问题忽略了。
2. **置信度写死 0.8**，`false_positive_likelihood` 永远是 `low`。这两个字段没有任何信息量。
3. **第一个命中就 return**，多规则命中信息丢失。一条请求同时是"SQL 注入 + 扫描器"时，你只看到了一半。
4. **正则写死**：加一条规则要改代码 + 发版。安全同学没法自助。
5. **`Severity` 与 `analysis` 是常量字符串**，不是从证据推出来的。换个 payload 结论文字一模一样，一看就是模板。

**改法**：规则外置成 JSON（`alertsage/rules/*.json`），命中收集全部而不是先到先得，置信度来自规则定义，判定交给独立的打分层。

### `app/main.py`

```python
@app.post("/analyze", response_model=AlertVerdict)
def analyze_alert(alert: AlertInput):
    result = detect_by_regex(alert)
    if result:
        return result
    return AlertVerdict(verdict="unknown", ...)
```

**问题**

- 接口只有一个，没有批量。真实现场是"一次导入几千条"，逐条 curl 不现实。
- 没有 `/health`，没法做探活/部署。
- 没有错误处理：字段缺失走 FastAPI 默认 422，但业务错误（比如时间解析失败）没有定义。
- 同步阻塞，没有并发控制；一旦接上有状态的检测（异常基线），多线程会出竞态。

**改法**：批量接口 + 汇总、健康检查、明确的 400/422/500 语义、状态串行化（见 `api/stdlib_server.py` 里的 `lock` 注释）、以及一个可选的 FastAPI 版本。

### `requirements.txt`

```
fastapi
uvicorn[standard]
pydantic
```

**问题**：不锁版本。半年后 `pip install` 可能装出跑不起来的组合。
**改法**：核心零依赖 + `requirements-api.txt` 列出可选依赖，`pyproject.toml` 里给版本下界。

## 三、最根本的问题：没有"研判"这回事

把上面的代码合起来看，它做的是：

```
输入 payload → 正则匹配 → 输出攻击类型
```

而蓝队同学实际做的判断是：

```
这条告警：来自谁？打哪个资产？有没有被拦？成功了吗？
          同类告警今天出现过几次？这个 IP 之前干过什么？
          如果是攻击，到哪一步了？该找谁、做什么？
```

**这中间的差距不是"再多写几条正则"能补上的，而是需要一个新的架构**：

| 能力 | v0.1 | 为什么必须有 |
| --- | --- | --- |
| 归一化 | 无 | 现场数据源五花八门，字段名都不一样 |
| 多维度检测 | 只有正则 | 单条规则看不出"同一 IP 5 分钟打 30 个路径" |
| 关联去重 | 无 | 不合并就会刷屏，合并了才能看趋势 |
| 可解释打分 | 命中即结论 | 结论不可解释 = 值班同学不敢用 |
| 评估 | 无 | 没有指标就无法证明改进了 |
| LLM 降级 | 无 | 模型一旦不可用，整个系统不能停 |

这就是 v0.2 的全部动机。

## 四、如果你只改三件事

按投入产出比排序，给"时间不够"的情况：

1. **加评估集**（半天）。哪怕只有 50 条手工标注，也能让"准不准"从感觉变成数字。面试时这句话值很多分。
2. **把规则外置**（半天）。JSON/文件加载，配 `rules --lint`。结构感立刻不一样。
3. **加证据链输出**（一天）。每条结论后面跟 3 条依据。这是"能解释"和"黑箱"的分界线。

LLM 排最后——它最容易写，也最容易被追问，而且没有前三条撑着，接上 LLM 只是把不可解释变得更贵。

## 五、招聘方视角

一个安全岗面试官看到旧版会想什么：

- "这个项目能跑吗？" → 没测试、没锁版本，不敢信。
- "它和网上的教程 demo 有什么区别？" → 看不出区别。
- "你说准确率高，依据呢？" → 没有。
- "如果误报很多怎么办？" → 代码里没有误报的概念。

看到 v0.2 会想什么：

- "有 132 个测试，CI 是绿的" → 能跑，可信。
- "合成数据集 94%，并且主动说明了偏乐观" → 知道边界，不吹。
- "分数构成能逐步追溯" → 想过产品怎么被信任。
- "LLM 有防幻觉校验和降级" → 想过线上会怎么坏。

**差别不在代码量，在于有没有"工程判断"。**
