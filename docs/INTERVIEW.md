# 面试讲稿

针对"大专、应届、安全方向"的实际场景写的。目标不是把你包装成专家，而是让面试官在 10 分钟内确认三件事：
**能干活、想过问题、讲得清楚。**

---

## 一、30 秒版（自我介绍里带一句）

> 我自己写了一个告警研判工具 AlertSage。起因是护网的时候每天几千条告警，大部分是扫描器和误报，一条条看很浪费时间。我做了个流水线：先统一不同设备的字段，再用规则和行为基线判断，最后给一个 0 到 100 的风险分和误报概率，每个分数都能说出依据。在 183 条标注数据上准确率 94%，单条 0.3 毫秒，132 个测试。

要点：**痛点 → 你做了什么 → 一个数字**。不要在这 30 秒里讲架构。

---

## 二、3 分钟版（面试官让你介绍项目时）

按这个顺序讲，每段一句，别背稿：

1. **背景**（15 秒）
   "护网的时候我在蓝队做告警研判，一天几千条，重复劳动多，真正复杂的攻击反而没时间看。"

2. **旧版的问题**（20 秒）
   "我第一版写得很简单，就是几条正则匹配 payload，命中就说是攻击。后来发现根本不能用：误报率极高，而且它只看单条告警，看不出'同一个 IP 五分钟打了三十个路径'这种事。"

3. **这一版怎么做的**（60 秒）
   "我拆成了几层：先把 Wazuh、ELK 这些不同来源的字段统一，然后检测层有三块——规则引擎、正则兜底、行为异常。规则改成 JSON 配置，安全同学自己就能加，不用改代码。检测完做关联去重，最后打分。
   打分这块我刻意把'是不是攻击'和'要不要现在处理'分开了：误报概率是一个维度，风险分是另一个。被 WAF 拦下的 Log4j 是真攻击，但不急；内网扫描器可能是误报，但也可能是横向移动的前奏。"

4. **验证**（30 秒）
   "没有数据就没法证明好不好用，所以我自己造了一套带标签的评估集，183 条。第一版跑出来准确率只有 70%，我看了混淆矩阵，发现问题是中危规则的基础分永远到不了判定线，调了阈值和'已拦截'的算法才到 94%。这个调优过程我写在文档里了。"

5. **边界**（20 秒）
   "它有两类明确会错的地方：搜索框里输入 union select 会被误判，规则没覆盖的攻击只会给'待复核'。我认为后者是对的——没证据就交给人，不能自动关单。"

这五段讲完，面试官基本会追问技术细节，主动权就在你这边了。

## 三、简历怎么写

不要写"独立开发告警研判系统"就完事，要带结构和数字。参考：

> **AlertSage · 蓝队告警研判引擎**（个人项目，Python，2026）
> - 针对护网期间告警量大、误报率高的问题，设计 `归一化 → 检测 → 关联 → 打分 → 叙述` 五层流水线，支持 Wazuh/Elastic/Suricata 多源接入。
> - 规则与代码解耦：16 条声明式 JSON 规则（含 ATT&CK 映射）+ 行为基线（频率/发散/端口/爆破），规则可由非开发人员维护。
> - 可解释打分：风险分与误报概率双维度建模，每个加减分输出证据，183 条标注集上准确率 94%、F1 95%、单条 0.3ms。
> - LLM 作为可选叙述层，含 JSON 校验、规则编号防幻觉、失败降级；无 API Key 亦可完整运行。
> - 132 个单元/接口测试，GitHub Actions CI，Docker 部署。

**不要写**："精通"、"深入理解"、"某安全大厂级"。应届生的可信度来自具体数字和具体取舍。

## 四、现场演示（如果允许带电脑）

三条命令，30 秒，别打开代码：

```bash
python -m alertsage demo                              # 单条研判 + 分数构成
python -m alertsage evaluate                          # 混淆矩阵
python -m alertsage triage -f data/samples/alerts.jsonl -o report.html   # 打开报告
```

演示时**边跑边解释输出**：先说"这里 70 分是怎么来的"，指着分数构成讲。这比讲架构有说服力。

如果对方没兴趣看，就别硬演示，直接回答问题。

## 五、高频追问与参考回答

### Q1：为什么不让 LLM 直接判定？现在大模型这么强。

> 我试过，三个原因放弃了：
> 一是不可复现，同样输入两次结论可能不一样，值班同学不敢信；
> 二是幻觉，它会编造不存在的 IP 和日志，安全场景里这个代价太高；
> 三是成本和延迟，几千条告警逐条调用不现实。
> 所以我的设计是确定性引擎做判定，LLM 只做"把证据翻译成人话"，并且加了校验：它引用的规则编号必须在证据链里存在，否则降级到模板。

### Q2：正则规则很容易被绕过吧？

> 是的，纯正则一定有绕过。所以它在我这儿是兜底层，不是主力。主力是三层叠加：规则 + 行为异常 + 关联。绕过单条 payload 容易，但"一个 IP 十分钟访问 40 个路径、失败 20 次"这种行为特征绕不掉。
> 另外我在文档里写了已知失败模式，比如搜索框输入 union select 会误判，这是文本匹配的固有缺陷，下一步要做 SQL 语法结构解析。

### Q3：准确率 94% 是怎么算的？数据哪来的？

> 数据是我自己按攻击类型和噪声类型构造的合成数据，183 条，每条有"该不该处置"的人工标签。
> **这个数字是偏乐观的**，我在 README 里明确写了不能当真实准确率用。它的价值是版本间回归对比——我改了打分逻辑，准确率掉了 20 个点我能立刻发现。
> 真实环境要拿客户脱敏告警重标注，我估计会掉到 75~85%。

（这个回答的重点是：主动承认局限，比硬吹分数可信得多。）

### Q4：那你怎么降误报？

> 三个层次：
> 一是信号层，识别扫描器 UA、404、已拦截、内网拨测这些噪声特征，直接降权；
> 二是关联层，同一个 IP 打同一个路径几十次，合并成一条而不是几十条；
> 三是白名单，长期噪声源直接配正则白名单。
> 另外我把误报概率单独建模，`fp >= 0.7` 直接判误报，不占用人。

### Q5：性能怎么样？十万条要多久？

> 单条 0.27 毫秒，十万条大概 30 秒，单核。
> 瓶颈是正则匹配不是 IO，所以加线程没用（GIL）。要更快就按 IP 或指纹分片到多进程，每个进程独立维护行为状态。
> 我实测过预编译正则的影响：不预编译 p50 会从 0.25ms 涨到 2ms 以上。

### Q6：这些东西 ELK / SIEM 不是都有吗？重复造轮子？

> 有重合，但侧重点不一样。ELK 强在存储和检索，告警规则要自己配；商业 SIEM 有内置规则但贵、不透明、不好改。
> 我做的是"研判"这一层——不是找告警，而是判断已有的告警值不值得看，以及为什么。
> 而且我的核心是零依赖的 Python 包，可以嵌进任何平台当分诊模块，不需要替换现有 SIEM。这个定位面试时我也说清了，不是要替代谁。

### Q7：状态存在内存里，多实例怎么办？

> 现在是内存态，单实例够用，重启会丢基线。这是有意的取舍——先验证研判逻辑对不对，而不是先做分布式。
> 我已经把状态访问收敛在 `Correlator` 和 `AnomalyDetector` 两个类里，并且留了 `snapshot()` 接口，换成 Redis 只改这两个类，业务流程不用动。

### Q8：规则怎么保证没写错？

> `alertsage rules --lint` 会检查 id 唯一性、严重度合法、正则能编译、MITRE 映射和处置建议是否完整，CI 里会跑。
> 另外每条规则加载时就预编译正则，写错了启动直接报错，不会等到线上才炸。

### Q9：如果 LLM 返回垃圾怎么办？

> 有四级兜底：JSON 解析失败、analysis 为空或超长、引用不存在的规则编号、网络异常——任何一项触发都降级到本地模板，并在结果里标 `degraded=true`。
> 模板叙述不需要模型，所以整条链路永远有输出。有测试专门覆盖这四种情况。

### Q10：这个项目你遇到最大的困难是什么？

> 打分那块。一开始我照着"命中就高分"的思路写，结果两个问题：一是重复计分，白名单降权之后又加了一次增量，风险分能算成负数；二是中危规则永远过不了判定线，因为基础分本身就低于阈值。
> 后来我把所有分数调整收进一个"账本"，乘法用 `scale`、加法用 `add`，账本和最终分数强制一致，还写了测试守着。阈值是照着真实分数分布反推的，不是拍脑袋。
> 这件事让我理解了：评分模型不是调参，是设计。

（这题答具体 bug 比答"架构设计"更可信。）

### Q11：你学历是大专，怎么看？

不回避，也别自我贬低：

> 学历确实是短板，我不回避。我能补的是手上有没有东西——
> 这个项目从数据模型到测试到 CI 都是我自己做的，代码开源，指标可复现，你可以随便问实现细节。
> 另外我护网是在蓝队一线做的，见过真实的告警长什么样，这也是我为什么知道误报比漏报更折磨人。

### Q12：这个项目是不是抄的 / 跟着教程做的？

> 第一版确实是照着教程的思路写的，就是几条正则加一个接口。后来发现没法用，才推倒重做。
> 现在的结构、打分模型、评估集都是我自己设计的，`docs/REVIEW.md` 里存了我对第一版的逐条批评，包括哪里错、为什么错。
> 如果你想验证，可以随便挑一个设计问我为什么这么做——比如为什么指纹里不放 URL。

## 七、如果面试后还想继续做（3 个月）

按对求职的加分排序：

1. **真实数据评估**（最重要）：找实习/护网拿到的脱敏告警，重新标注 200 条，跑出真实指标。这是从"玩具"到"能用"的分水岭。
2. **规则反馈闭环**：人工复核结论回写，自动调整规则 confidence。能讲"数据驱动"。
3. **SIGMA 规则导入**：直接吃社区规则集，规则数从 16 变几千，覆盖度立刻不一样。
4. **简易前端**：告警队列 + 一键采纳/驳回。有界面截图，简历和 GitHub 的观感完全不同。
5. **写一篇技术文章**：讲"为什么我不让 LLM 做判定"，发在掘金/知乎。这是最省力的曝光方式，比 star 有用。
