# 设计说明

写给想改这个项目的人，也写给面试时追问实现细节的人。所有内容与代码一致，改代码时请同步改这里。

---

## 1. 为什么分层

```
normalize → detect → correlate → score → narrate → TriageResult
```

每层只依赖上一层的数据结构，原因：

- **可测试**：`score()` 不碰 IO，纯函数，输入 `Alert + [Detection]` 输出分数，132 个测试里一半是这种纯函数测试；
- **可替换**：换规则库不动打分，换 LLM 不动检测，接 Redis 不动流程；
- **可解释**：每层都产出结构化中间结果，出问题能定位到"是没检测到"还是"检测到了但分数算错"。

失败的传播也被隔离：单个检测器抛异常只会记录到 `meta.detector_errors`，不影响其他检测器和整批判研。

## 2. 归一化

### 字段别名表

```python
FIELD_ALIASES = {
    "src_ip": ("src_ip", "source_ip", "srcip", "source.ip", "src.ip", "data.srcip", "client_ip"),
    ...
}
```

按优先级依次尝试，支持点号路径取嵌套字段。新增数据源 = 加一张表，不改检测逻辑。

### 时间解析

必须处理：ISO8601（含 `Z`）、带时区偏移、空格分隔、nginx/apache 的 `10/Sep/2026:14:22:31 +0800`、秒/毫秒/微秒/纳秒时间戳。

按数量级判断单位：`>1e17` 纳秒、`>1e14` 微秒、`>1e11` 毫秒、其余秒。

**解析失败抛 `NormalizeError`，绝不回退到 `now()`**。原因：错误的时间会让窗口关联和频率基线失效，而且这种错误是静默的——一旦用 `now()` 兜底，你永远发现不了数据源时间字段配错了。

### IP 归类

`ip_scope()` 返回 `public / private / loopback / reserved / unknown`，用于误报判断："内网扫描器打内网"和"公网 IP 打生产库"不是一回事。

## 3. 规则引擎

### 条件 DSL

```json
{"all": [
  {"field": "dst_port", "equals": 22},
  {"any": [{"text": "regex:(?i)failed password"}]}
]}
```

求值是纯递归，`_eval_node` 返回 `(bool, [命中说明])`。第二个返回值很关键：每一条叶子条件命中都会生成一句人话，直接进证据链，不需要事后拼字符串。

### 为什么预编译正则

`Rule.compile()` 在加载时把所有正则编译好，缓存在 `_compiled`（key 是节点的 JSON 序列化）。不预编译的话，183 条样本 × 16 条规则 × 每条 2~3 个正则 = 上万次重复编译——实测 p50 从 0.25ms 涨到 2ms 以上，量级差别。

`{"text": ...}` 节点的正则在 `_regex_for()` 里惰性编译并缓存，因为 `text` 会被展开成 `{"field":"text","regex":...}` 的临时叶子节点，key 稳定，缓存有效。

### 权重设计

`severity` 定基础分，`confidence` 定可信度，`weight_delta` 做规则级微调（扫描类 -6，因为盲扫绝大多数无价值）:

```
base = SEVERITY_BASE[severity] * confidence
```

## 4. 打分模型

### 账本

所有调整走 `_Ledger`，只有三个方法：`start` / `add` / `scale`。这是被 bug 逼出来的设计——早期版本里同时"乘系数"和"加增量"，出现了 `risk = 0.85*risk` 之后又 `risk += (0.85*risk - risk)` 的重复计分，白名单场景甚至能算出负数。

现在 `scale(factor, extra)` 统一算 `target = risk*factor + extra`，再把 `target - risk` 记为增量，账本和最终分数永远一致（有测试 `test_breakdown_matches_risk` 守着）。

### 公式

```
risk = base
     + Σ 独立规则加分（每条 +6，上限 +18）
     + 跨类别加分（+4）
     + 规则 weight_delta
     + 行为异常加分（认证爆破 +10，其他 +4）
     ├─ × 资产重要度（0.6 ~ 1.2）
     ├─ × 0.35（白名单）
     ├─ × 0.85（窗口内重复）
     ├─ × 0.85 - 4（已被 WAF/IPS 拦截）
     + 12（高危告警疑似突发）/ +4（低危）
     - 6（低危 + 公开扫描器 UA）
     - 4（recon 类 + 404）
```

### 为什么阈值是 45 / 22

由分数分布反推：

| 场景 | 计算 | 分数 |
| --- | --- | ---: |
| SQL 注入（high × 0.86） | 72 × 0.86 | 62 |
| XSS（high × 0.75） | 72 × 0.75 | 54 |
| 路径穿越（high × 0.8） | 72 × 0.8 | 58 |
| 目录扫描（low × 0.62，- 6 - 4） | 22 × 0.62 - 10 | 4 |
| 单次登录失败（medium × 0.7） | 48 × 0.7 | 34 |
| 被拦截的 XSS | 54 × 0.85 - 4 | 42 |
| 无命中（正常响应） | 基线 | 15 |

- `TP = 45`：high 级命中稳定过线；medium 单条（34 分）不过线，符合"中危单条交给人"；
- `FP = 22`：低危探测 + 抑制项后落在 4~15，稳定判误报；
- 中间地带（22~45）就是 `needs_review`——这是**故意的缓冲区**，不是调不出来。

**这条边界被两次评估迭代验证过**：第一版阈值 55/25 时 medium 级 XSS 永远过不了线（因为 medium 基础分 48 本身就低于 55），三分类准确率只有 70.6%。改成 45/22 并把"被拦截"从纯减分改成乘系数后升到 93.99%。

### 风险分 vs 误报概率

```
fp = 1 - primary.confidence
   - 0.08（跨类别交叉）
   - 0.12（突发）
   - 0.05（核心资产）
   + 0.45（白名单）
   + 0.12（重复）
   + 0.08（已拦截）
   + 0.20（低危 + 扫描器 UA）
   + 0.15（recon + 404）
```

判定顺序：

```
fp >= 0.70                    → false_positive
risk >= 45                    → true_positive
risk <= 22 且 fp >= 0.50      → false_positive
其余                           → needs_review
```

先看 fp 是有意的：**"非常确定是噪音"比"分数不高"更有决策价值**。

## 5. 关联与状态

### 指纹

```python
fingerprint = sha1(src_ip | dst_ip | dst_port | alert_type)[:16]
```

**刻意不含 `target_url`**。真实场景是"一个 IP 刷几百个路径"，按 URL 分组会导致每条都是新告警，去重和突发识别全部失效。目标发散由 `Incident.targets` 记录，细粒度异常由 `ANOM-FANOUT` 负责。

### 窗口与突发

- 窗口默认 600 秒，`_prune` 按 `max(now, max_seen)` 裁剪，**乱序输入也能正确处理**（真实数据流经常轻微乱序）；
- 同指纹累计 ≥ 8 次标记 `burst`，打分层据此 +12（高危）或 +4（低危盲扫）；
- `incident_id` 带自增序号（`INC-0003-ab12cd`），窗口过期后同指纹重开不会复用 id。

### 状态边界

内存态，进程重启即丢。这是刻意的取舍：单实例/离线场景够用，多实例要换 Redis。接口预留 `snapshot()`，替换成本低。

## 6. LLM 层

```
should_call?  ── no ─→ 模板叙述（永远不会失败）
     │ yes
     ↓
provider.complete()  ── 异常 ─→ 降级 + degraded=true
     ↓
_parse_and_validate()
     ├─ 非 JSON / analysis 空 / 超长  → 降级
     ├─ 引用了不存在的规则编号        → 降级（防幻觉）
     └─ 通过                          → 使用，source=llm
```

`should_call` 的三条门槛：LLM 未启用、`verdict == false_positive`、`risk < llm_min_risk_for_call` 都不调用。误报不需要写分析，低危不值得花 token。

### 防幻觉为什么只查规则编号

LLM 最容易编造的是"具体事实"：IP、域名、文件路径、日志片段。IP/域名无法可靠校验（可能是真实情报），但**规则编号是封闭集合**——文中出现 `WEB-FAKE-999` 而证据链里没有，就是编的。

这条校验的成本是 3 行正则，收益是把"模型胡说八道"从不可控变成可检测。

## 7. 性能

| 环节 | p50 |
| --- | ---: |
| 归一化 | ~0.02 ms |
| 规则匹配（16 条，预编译） | ~0.1 ms |
| 行为基线 | ~0.01 ms |
| 打分 | ~0.02 ms |
| 模板叙述 | ~0.02 ms |
| **合计** | **0.25 ms** |

183 条批量处理总耗时约 50 ms。瓶颈在正则匹配，而不是 IO——所以 `pipeline.triage_batch` 没有做多线程/多进程，因为 Python GIL 下正则匹配本来就串行，加线程池只会增加复杂度。

真到需要 10k QPS 时，正确的做法是按告警指纹分片到多进程（每个进程独立维护状态），而不是在单进程里堆线程。

## 10. 已知失败模式

1. **文本匹配的固有缺陷**：搜索框输入 "union select" 会被判注入。计划引入 SQL 语法结构解析。
2. **规则覆盖不到的攻击**：DNS 隧道等只到 `needs_review`。这是**预期行为**——宁可交给人，不可自动关闭。
3. **冷启动**：突发的前几条告警没有行为证据，只能看单条特征。
4. **合成数据偏差**：指标偏乐观，真实数据上会掉。
5. **状态不持久**：重启后基线清零，短时间内可能重复研判同一批告警。
